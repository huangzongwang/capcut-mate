# 视频制作模块可行性与开发计划

编制日期：2026-09-16。
依据：本地 capcut-mate 源码，以及“视频平台原型2026091501”的 index.html、app.js。
范围：爆品参考视频分析与裂变、脚本分镜自动选素材、编辑预览、导出审核。不在本次实施业务代码。

## 1. 结论与边界

技术上可行，但不是把原型直接连接现有 API 就能完成。capcut-mate 适合承担“剪映草稿生成与导出适配”，不承担视频理解、素材管理和智能决策。

推荐第一版采用“真实素材检索 + 规则约束编排 + 人工确认 + 基础自动渲染”。先不把 AI 视频生成作为成片的必经步骤。

本计划将“爆品”理解为已由业务选定的优质带货参考视频。仅凭视频内容可以分析结构和表达，不能证明销量、转化率或者爆款原因；这些结论需要投放与交易数据支持。

| 目标 | 可行性判断 | 第一版边界 |
|---|---|---|
| 分析视频脚本、镜头、结构 | 可做，识别结果需校正 | 语音转写、画面文字识别、镜头切分、结构标注 |
| 替换空境并批量裂变 | 优先实施，容易控制质量 | 保留原结构与音频，替换人工确认可换的画面 |
| 脚本自动拆镜并选素材 | 可做，质量取决于素材覆盖 | 候选推荐、自动编排、人工换镜 |
| 保留人物但更换背景 | 独立高风险能力 | 不等同于空境替换，后续专项验证 |
| 根据 AI 生成缺失镜头 | 可以作为补充路线评估 | 不默认触发，单独预算、授权和审核 |
| 保证裂变后仍是爆款 | 不可承诺 | 记录版本与投放表现，逐步迭代 |
| 完整复刻剪映网页编辑器 | 不适合作为首版目标 | 仅支持分镜级编辑和限定样式 |

## 2. 原型与现有工程审计

### 2.1 原型可以继承的产品流程

- 导入视频：上传 → 提取脚本 → 分析框架 → 标记镜头 → 确认结果。
- 脚本制作：输入/选择脚本 → 设置时长画幅 → 限定素材范围 → 分镜匹配 → 编辑。
- 制作工作台：左侧脚本段落、中间预览、右侧候选素材、下方多版本时间线。
- 裂变：设置数量、替换素材、可选调整顺序、生成多个方案。
- 输出：参数确认 → 后台任务 → 成片预览 → 人工审核 → 成品库。

app.js 中的匹配分数、裂变相似度、任务进度和生成结果主要由固定数据与定时器模拟，不能视为已实现后端能力。分析弹窗已提出“只保存原视频入出点、不重复切出文件”，应保留这个设计。

### 2.2 可复用与必须补齐的能力

| 能力 | 当前依据 | 接入策略 |
|---|---|---|
| 创建和保存剪映草稿 | create_draft、save_draft、get_draft | 复用，定位为导出适配层 |
| 视频、图片、音频、字幕编排 | add_videos、add_images、add_audios、add_captions | 复用，建立统一时间线转换 |
| 动画、花字、滤镜、特效 | 对应 get_* / add_* 接口 | 只开放验证过的白名单 |
| 任意素材源区间选取 | add_videos.py:479 将 source_timerange.start 固定为 0 | 扩展源入点与源时长，补测试 |
| 渲染视频 | video_task_manager.py 的 Windows 剪映自动化 | Windows 专用节点，不在 Linux 容器里调用 |
| 任务恢复 | video_task_store.py 仅持久化完成/失败结果 | 平台另建持久任务与重启恢复机制 |
| 视频内容理解 | 当前业务服务未提供此链路 | 新增分析 Worker |
| 片段级素材检索与自动匹配 | 当前业务服务未提供此链路 | 新增素材索引与匹配服务 |
| 浏览器合成预览 | 当前无真正时间线播放器 | 新增低清代理渲染与播放器 |

部署注意：本地 compose 使用远程 latest 镜像，修改本地源码不会自动进入该镜像。开发接入时需构建自有版本并固定镜像标签。现有 compose 对 capcut-mate 限制 1 CPU/1GB；不能据此推断视频分析和渲染所需资源已满足。

## 3. 链路 A：参考视频分析与裂变

### 3.1 分析过程

1. 上传参考视频，保存原文件、校验和、授权信息及产品标识。
2. 探测时长、帧率、旋转、画幅和音轨；生成代理视频、封面、波形。
3. 镜头边界检测形成物理镜头；语音识别形成带时间戳逐字稿；画面文字识别单独保存。
4. 多模态分析提取人物、产品、动作、场景、景别、运镜、情绪、可见文字和关键物品。
5. 基于画面及文案划分开头钩子、痛点、卖点、证明、行动号召等语义段落，不强制每个视频都有固定四段。
6. 人工校正边界、文案、SKU、镜头角色，并确认允许替换范围。

物理切镜与语义分段不是同一件事，一个段落可以包含多个镜头。保留两套时间边界及其对应关系。语音和字幕冲突时保留来源，不直接互相覆盖。

### 3.2 镜头替换政策

| 镜头类别 | 默认政策 |
|---|---|
| 街景、天空、环境空镜 | 可推荐替换，但须匹配场景和节奏 |
| 产品补充画面、手部操作 | 有条件替换：必须检查 SKU、动作和上下文 |
| 真人对口型口播 | 锁定；不随意改时长、顺序和配音 |
| 核心产品、价格、证据、CTA | 默认锁定，业务人员明确批准才可改 |
| 前后有动作连续性的镜头 | 作为关联镜头组一起锁定或替换 |

“空境”是没有主体人物的环境镜头，不应把“没有检测到脸”直接判为空境。产品特写、手部操作、背影都可能承担重要内容。

### 3.3 裂变生成

- 首版默认保留旁白、总时长、段落顺序、核心产品和 CTA，仅替换可换画面。
- 在指定素材范围内检索同类镜头，检查时长、画幅、产品、人物、场景和授权。
- 每个可换镜头先取少量合格候选，再按整条片子的连贯性和差异性组合。
- 镜头重排仅允许在标记为可交换的段落内部进行，不能随意打乱产品使用步骤。
- 对锁定镜头、镜头组和原声建立显式约束；随机种子与选材依据随版本保存。
- 素材不足时返回可生成数量与原因，不强行凑数、不越过素材范围、不自动调用付费生成。

原型“最大画面相似度 30%”不能直接作为平台查重承诺。首版建议展示可解释的“按时长计算的原画面保留率”和“重复片段率”；语义相似度单独作为内部排序分数，不能混成一个百分比。

例如总时长 30 秒，锁定画面占 18 秒，则原画面保留率至少 60%；系统应提示用户无法满足 30% 的保留率目标。

### 3.4 已压制视频的特殊限制

- 硬字幕已经成为画面像素，不能像字幕轨一样无损删除。优先使用无字幕母版，否则首版保留或提示人工处理。
- 原视频旁白、音乐、音效可能混在一条音轨，不能假设能分别编辑。首版保留完整混音；换配音另立模式。
- 替换画面时若保留原混音，应检查开瓶、敲击等音效与新动作是否冲突。
- 不从一条 MP4 自动恢复原剪映的图层、特效参数和可编辑字幕。

## 4. 链路 B：脚本分镜与自动选素材

1. 输入脚本、产品信息、目标时长、画幅、声音来源及允许使用的素材。
2. 生成结构化段落和镜头需求，给出预计时长、画面描述、主体、动作、景别、产品和禁用内容。
3. 确认旁白或生成配音；依据实际音频时长对齐字幕与镜头，不只按字数估算。
4. 检索候选片段，返回每镜头前 3～5 个候选及匹配理由。
5. 自动选出一套时间线，做整片重复、连贯性、时长和产品一致性检查。
6. 用户换镜、改源入出点、锁定镜头、调整音量、保存版本。
7. 生成代理预览，通过后输出 MP4 和/或剪映草稿。

### 4.1 素材必须索引到“片段”

不能只给整条长视频贴标签。素材索引至少包含：

- 原素材 ID、片段 ID、源入点/出点、帧率、时长、分辨率、代理地址和封面。
- 场景、人物、主体物品、产品/SKU、动作、景别、运镜、语音、画面文字。
- 清晰度、抖动、字幕/水印标识、主体裁切风险。
- 可用项目、授权范围、过期时间、所属租户。
- 标签来源、置信度、人工校正结果、分析模型与版本。

检索先执行租户、授权、SKU、素材范围、可用时长等硬过滤，再以标签/文本/向量召回候选，最后评估画面和上下文。无合格候选时返回缺镜，不能只靠最高分硬选。

为避免“人物拿错物品”：对关键物品设置明确要求和排除条件，结合多帧检查；产品镜头优先采用已确认的同 SKU 实拍片段。涉及关键物品但识别低置信度时必须待审核，不能自动放行。

### 4.2 时长处理

优先选足够长的自然片段，再裁剪；允许轻微变速时必须受配置限制。口播、嘴型和动作证据片段默认不变速。素材太短则换素材或拆镜，不默认定格、循环和大幅慢放补足。

## 5. 建议架构与渲染方案

建议作为待验证技术方案：保留 FastAPI，新增一个制作业务服务和后台 Worker；使用 PostgreSQL 保存业务与任务数据，按检索量决定是否启用向量扩展；素材与结果进入对象存储。首版不拆成大量微服务。

```text
原型改造后的 Web 工作台
          |
制作业务 API：项目 / 脚本 / 素材 / 时间线 / 版本 / 审核
          |
数据库 + 对象存储 + 持久任务
          |
分析与匹配 Worker → 规范化时间线
                         |
             +-----------+-----------+
             |                       |
      基础渲染 Worker          capcut-mate 适配
      代理预览 / MP4           可编辑剪映草稿
                                     |
                           可选 Windows 剪映导出
```

基础渲染建议验证 FFmpeg 路线，镜头检测建议验证 PySceneDetect 路线；语音识别、OCR、多模态理解与配音先以统一输入输出接入一种服务/实现，选型由真实素材 PoC 决定。本轮在线检索未返回可用资料，因此不将具体版本、兼容性、许可或供应商报价视为已核实。

### 5.1 两条导出路径

- **默认基础路径**：Linux Docker 内渲染标准裁剪、拼接、缩放、基础转场、音频和字幕；先生成低清代理供浏览器播放，再输出高清成片。
- **剪映增强路径**：生成剪映草稿；确需剪映专属效果时交给 Windows 节点导出。先验证当前剪映版本、资源、字体、登录状态与界面自动化稳定性。

这也修正前面的预览方案：使用现有 gen_video 确实需要 Windows，但新增基础渲染器后，网页预览不必依赖 Windows。

两条路径不能承诺花字和专有滤镜完全一致。首版只开放基础路径支持的效果；剪映专属效果显示明确标识，其最终预览应播放实际剪映导出的文件。

单 Windows 节点中的剪映导出必须串行；扩容需独立桌面节点与外部调度，不能简单增加同一桌面的 API Worker。现有线程锁不能替代跨进程、跨节点锁。

### 5.2 统一时间线

平台以自身结构化时间线为唯一业务源，不把剪映 JSON 当业务数据库。

核心字段包括 project_id、version_id、segment_id、shot_id、asset_id、source_in_us、source_out_us、timeline_start_us、timeline_duration_us、speed、crop、volume、locked、selection_reason，以及字幕、配音、音乐、效果、画布参数。

时间统一用整数微秒；渲染时按目标帧率对齐边界。源区间与时间线区间必须分开，验证变速关系、素材越界和转场重叠。

每次修改生成新版本；每次渲染绑定不可变版本快照。代理预览与最终导出必须使用同一快照，旧预览不能显示成新方案的结果。

### 5.3 capcut-mate 的必要改动

1. 为 add_videos 增加兼容旧请求的源入点、源时长支持，明确速度、目标时长与源区间约束。
2. 视频、音频分别验证源裁剪能力；相关字段需贯穿 schema、service、工具参数转换与文档。
3. 平台编辑先更新统一时间线，再创建新草稿导出，不依赖尚未确认存在的任意片段更新/删除 API。
4. 适配层负责 video_infos 等 JSON 字符串序列化、微秒换算及效果映射，前端不直接拼底层请求。
5. 使用所有 Worker 均可访问的素材地址，不使用容器/其他机器不可达的 127.0.0.1。
6. gen_video 的 UUID/API Key 与 ENABLE_APIKEY 配置按部署模式核验；它不是素材理解模型的密钥，不能替代 ASR/OCR/模型服务接入。

## 6. 数据与接口

建议业务实体：Project、Asset、AssetClip、Analysis、ScriptVersion、Shot、TimelineVersion、Job、Render、Review。各实体记录租户、操作者、创建时间与来源版本。

建议新增接口，以下不是当前已有接口：

| 接口 | 职责 |
|---|---|
| POST /api/assets、GET /api/assets | 上传登记、素材查询 |
| POST /api/analyses、GET /api/analyses/{id} | 发起分析、读取带时间戳结果 |
| PATCH /api/analyses/{id} | 人工确认识别与镜头边界 |
| POST /api/projects/{id}/storyboards | 脚本生成分镜需求 |
| POST /api/projects/{id}/matches | 指定素材范围，生成候选 |
| POST /api/projects/{id}/variants | 受约束生成裂变版本 |
| GET/PUT /api/projects/{id}/timeline | 读取/保存时间线，带版本冲突校验 |
| POST /api/projects/{id}/renders | 指定版本与导出类型 |
| GET /api/jobs/{id} | 分阶段状态、错误、进度及结果 |
| POST /api/renders/{id}/reviews | 审核意见、通过/退回 |

任务需持久化输入、状态、当前阶段、心跳、尝试次数和结果引用；支持取消、超时、有限重试和重启恢复。外部付费请求记录供应商任务 ID；不确定是否已提交成功时先查询，不盲目重试计费。

安全要求：租户隔离、项目级素材权限、上传大小与媒体类型校验、下载地址防 SSRF、限额和限流、私有素材签名地址、服务端密钥、审计日志。草稿与素材清理需尊重项目引用，不能沿用临时草稿清理策略删除仍在使用的资产。

## 7. 分阶段排期

以下为工程估算，不是已验证工期。假设 1 名前端、1 名业务后端、1 名音视频/AI 工程师，以及兼职测试/产品；模型采用已有服务或成熟实现，不训练自有模型。外部接入、数据授权和素材准备及时到位。

| 阶段 | 时间估算 | 交付与通过条件 |
|---|---|---|
| P0 技术验证 | 第 1 周 | 选 10 条参考视频、100 个候选片段；跑通一条真实裂变与一条脚本成片；验证非零源入点、硬字幕/混音限制、渲染选择 |
| P1 数据底座 | 第 2～3 周 | 上传、代理、片段索引、分析编辑、素材范围、持久任务；刷新页面和进程重启不丢业务状态 |
| P2 脚本制作 | 第 4～5 周 | 脚本分镜、音频对齐、候选推荐、人工换镜、时间线版本、可播放代理、基础 MP4 与草稿 |
| P3 视频裂变 | 第 6～7 周 | 锁定镜头、等长空境替换、批量去重、容量提示、版本对比与审核 |
| P4 试运行 | 第 8～9 周 | 真素材回归、权限、成本、负载、重试恢复、监控、部署说明 |

如果空境裂变是近期唯一业务重点，P0 后可优先实现“人工标记可换镜头 + 指定候选库 + 保留混音 + 批量替换”的窄版，预计第 3～4 周给出可试用闭环；自动结构分析和脚本选材随后补齐。

Windows 专属渲染作为可选并行验证，不阻塞基础 MP4 路线；若要求第一版完整支持专有特效，需在 P0 后重新评估排期。单人开发不能直接套用上述多人排期。

## 8. 验收与评估

以下是建议目标，需 P0 数据集评审后定版，不代表当前已达到。

- 固定评测集覆盖空境、产品特写、口播、连续动作、硬字幕、无语音、短素材、混合帧率与画幅。
- P0 起由业务标注可替换区间、正确产品和可接受候选，避免只看模型自评分。
- Top-3 素材候选人工可用率目标不低于 85%；统计口径为需求镜头中至少存在一个可用候选的比例，并同时报告缺镜率。
- 锁定镜头与指定素材范围约束通过率 100%；关键 SKU 错误零容忍，低置信度不进入自动审核通过。
- 无合格素材时必须报告缺镜；生成数量不足时解释约束，不重复凑数。
- 标准支持范围内批量导出成功率目标不低于 95%；公开样本量和失败原因。
- 逐帧检查源入点、片段顺序、转场边界、黑帧、裁切、字幕、安全区和音画同步；时间误差按帧定义。
- 任务重试不重复扣费或产生成品记录；重启可恢复，取消任务不继续无控制地消耗资源。
- 相同版本的代理与成片内容对应；实际预览可播放、可定位镜头，不能用进度动画替代渲染。

性能不预先承诺固定“几分钟成片”：P0 实测每分钟素材分析耗时、每秒成片渲染耗时、单机并发与内存峰值，再定容量。单个串行渲染节点日容量按“可用秒数 ÷ 实测平均任务秒数 × 利用系数”估算。

## 9. 成本、风险与实施决策

单条成本应拆分：首次入库分析 + 本次理解/检索 + 可选配音 + 渲染 + 存储/流量 + 重试。入库结果按文件哈希和分析版本复用，裂变不重复分析全部素材；基础方案不含 AI 视频生成费用。

原型中 30/45/120 点等是展示数据，不是可直接沿用的计费规则。上线前记录真实供应商调用与资源耗时，设置项目预算与批量数量上限。

主要风险及策略：

- 素材不足：先评估候选覆盖率，支持人工补充；自动化能力不能弥补不存在的产品画面。
- 分析错误：保留证据时间戳、置信度和人工校正；不让模型擅自决定锁定镜头可替换。
- 生成幻觉：第一版优先实拍；以后新增 AI 补镜也需独立验收人物、手持物品与包装。
- 渲染不一致：限定支持的样式，建立时间线到两种输出的对照样例。
- 桌面导出故障：Windows 单节点串行、健康检查、限次重试、失败截图和人工接管。
- 内容来源风险：仅纳入业务确认可用的素材，保存授权来源；不承诺低相似度即可避免平台重复内容判断。

立项前待确认但不影响先做 P0 的事项：

1. 首批品类、SKU 与可提供的参考视频、无字幕母版和素材量。
2. 首版是否只换画面，是否必须改配音或删除已有字幕。
3. 输出以 MP4 为主，还是必须剪映工程和专属特效。
4. 日成片数量、平均时长、等待时间及部署机器配置。
5. 外部模型调用、素材上传范围和费用预算。

推荐决策：先投入一周 P0，以真实素材验证“两条完整链路”，然后按评测结果确定 8～9 周 MVP。第一版的关键不是增加更多特效，而是源区间准确、产品不串、素材选得对、音画对齐、预览可用和任务可恢复。
